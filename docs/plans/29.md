# Write-only tables and the unpersisted companion seq

Issue: #29 · Track: small · Branch: `issue/29-companion-seq`

## 1. Problem

The issue says `stale_events` and `companion_events` are written and never read, and the
companion's `State.last_seq` is never persisted after pairing. Reading the code shows more:

- `State.last_seq` is written as 0 at pairing (`crates/rubato-companion/src/main.rs:72`) and never
  again, so the companion's envelope sequence restarts at 1 on every start (`server_link/client.rs`
  `Client::new(start_seq)`).
- The server drops any envelope whose `(companion_id, seq)` it has already recorded and answers
  with a bare `Ack` (`crates/rubato-server/src/companion_link/ws.rs`, `store.rs:19` `INSERT OR
  IGNORE`). So after a companion restart its `Hello` gets no `Welcome` and its session snapshots,
  hooks and stale events are discarded until the counter passes the previous run's high-water mark.
  **This is a correctness bug, not tidying.**
- `companion_events` is therefore not write-only: it is the dedupe key. Only `stale_events` is
  never read.

**Acceptance criteria** (from the issue)

- [x] **AC1** — `State.last_seq` is persisted, so a restarted companion does not reuse sequence numbers.
- [ ] **AC2** — `stale_events` and `companion_events` are either read or dropped. *(Not met as written: both tables are kept and documented as write-only audit records, the choice approved on 2026-11-10.)*

Prior art: design #20 §11; ADR 0012 (websocket transport, sequence numbers and acks).

## 2. Spec

### 2.1 What the change does

- **S1** — When the companion starts, every envelope it sends has a sequence number higher than any it sent in an earlier run: it reserves numbers in blocks of 1000 in its own file `seq.json` in the state dir (`reserved_to` = the highest reserved number) before using them, and a new run starts above the last reservation. The first block is reserved before any task starts, so a state dir that cannot be written stops `run` at once with an error. (AC1)
- **S2** — When there is no `seq.json` yet (a pairing made before this change, or a fresh one), the first run starts from the current unix time in seconds, which is above anything a companion counting from 1 has plausibly sent, so existing pairings recover without re-pairing or editing the server's database. (AC1)
- **S3** — When a companion is paired again on a machine that already has state, the reservation is kept: `pair` never touches `seq.json`, and `run` never rewrites `companion.json` (the file with the pairing token). (AC1)
- **S4** — When a reservation cannot be written while the companion runs, the server link ends with that error instead of retrying as if the connection were lost; it is an essential task, so the companion logs `rubato.task.exited` and exits non-zero.
- **S5** — When the server receives a `Hello` whose sequence number it has already recorded, it logs `warn!` with the companion id and seq and counts `rubato.events.dropped{rubato.reason="replay"}`; the companion, on getting a bare `Ack` for its hello instead of a `Welcome`, logs `error!(start_seq, reserved_to, "hello treated as a replay")`. A hello is never in the outbox, so a replayed hello always means a sequence collision; ordinary outbox replays after a reconnect stay quiet.
- **S6** — The server keeps `companion_events` (it is the replay dedupe key) and `stale_events` (no reader; kept as the audit record of a never-silent event); the store's module doc says so. Nothing is dropped. (AC2 as amended by D2)

## 4. Caveats triage

- Idempotency: the dedupe key `(companion_id, seq)` is unchanged; this change restores its precondition (a companion never reuses a seq). A crash between reserving and sending wastes at most one block; gaps are harmless (the server takes `MAX`).
- Concurrency: `run` writes only `seq.json`; `pair` writes only `companion.json`. A `pair` while the daemon runs can no longer be undone by the daemon rewriting the old token. The reservation write is a small synchronous file write once per 1000 envelopes, on the client task.
- Contract compatibility: no field added, removed or changed in meaning. ADR 0012 already asks for increasing sequence numbers; the companion now honours it across restarts. `rubato.reason="replay"` is a new value of an existing attribute.
- Schema change: none (S6 keeps both tables).
- Observability: O1, O2. The replay signal is on the hello only, so normal outbox replays do not raise it. Both sides emit the heartbeat metric, so a fresh heartbeat panel does not rule a collision out; O2 does not rely on it.
- Log level (project): every signal in §2.4 is `info` or above.
- Telemetry names (project): no new name; one new value of `rubato.reason`.
- Testability: the reservation takes the state dir and a clock value as inputs.
- Seam O-row (project): `companion-server` has one.
- n/a: Boundaries, Authorisation, Cost, Derived not stored, Own tmux only, Check reports its count — no new entry point, table or check.

## 7. Decisions

- **D1** — the companion saves its sequence in blocks · the person chose this on 2026-11-10 · because the wire format and the server stay unchanged · rejected: the server exempting `Hello` from dedupe and the companion jumping to `Welcome.last_seen_companion_seq` (changes behaviour on the seam on both sides; full track).
- **D2** — keep `stale_events`, document it · the person chose this with D1 · because dropping it is a non-additive migration (full track) for a table that costs nothing · rejected: a migration that drops it.
- **D4** — the reservation lives in its own file · because `State::save` truncates and rewrites `companion.json`, so a failed write would destroy the pairing token, and a daemon rewriting it could undo a re-pair · rejected: `last_seq` inside `companion.json`.
- **D3** — seed from the clock when nothing is reserved · because without it every existing pairing still collides once after upgrading, which is the bug · rejected: asking users to delete `companion_events` rows by hand.

## Review outcome

design-reviewer, 2026-11-10: 3 blockers; all taken. The central claim was confirmed against the code, and heartbeats are lost in the collision window too.

- **Spec check:** Does: ok apart from S4's wording on `stale_events`. We'll know it works: the S3 row could not fail (the Gherkin pairing step never runs `main.rs`). Must not break: no guard for the pairing token, which `run` would have rewritten. Debug at 3 am: O1's signal was not on the failure path (the client retries on any error); O2 could not tell a collision from a normal outbox replay, and its remedy could recreate the bug.
- **Track check:** small holds: no migration, protocol, consumer, dependency or auth change; ADR 0012 already asks for increasing sequence numbers.
- **Fixed:** `seq.json` with an atomic write (D4, N3); the first block reserved in `start`, and a reservation error ends the client (S1, S4, O1); pairing moved into the slice with a test (S3); the replay signal keyed on the hello, counted as a drop, with a companion error line (S5, O2); the remedy names `pairings.last_companion_seq`.
- AC2 is amended by D2: `stale_events` is kept with no reader, as an audit record.
