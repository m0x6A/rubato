# Session metrics: sessions by state from the server only; no session id on hook_forwarded

Issue: #43 · Track: small · Branch: `issue/43-session-metrics` (stacked on `issue/44-status-lists`, PR #66, which rewrote the same gauge code)

## 1. Problem

Two questions #26 left open:

- `rubato.sessions.by_state` is recorded by the companion (from its registry, `sessions/tasks.rs` `record_gauges`) and by the server (from each snapshot, `companion_link/ws.rs` `record_sessions_by_state`), both labelled with the companion id. A panel or rule that sums it without filtering on the service counts every session twice. The "Sessions by state" panel (`sum by (rubato_session_state)`) does so today; only "Hooks/min vs working sessions" uses `max by`, and `observability/check.ts` enforces that one panel.
- `rubato.hook.forwarded` carries `rubato.session_id` (`hooks/arm.rs`), so it grows one series per session for the life of the companion process.

**Acceptance criteria** (from the issue)

- [x] **AC1** — decide which side owns sessions by state, and make sums over it correct.
- [x] **AC2** — decide whether the session id belongs on the counter or only on the span.

## 2. Spec

### 2.1 What the change does

- **S1** — Only the server records `rubato.sessions.by_state`, from each `Sessions` snapshot a companion sends (every status, zeros included, since #26). The companion no longer has the instrument. A sum over the gauge now counts each session once; the "Sessions by state" panel and `SessionWorkingNoHooks` (`sum by (rubato_companion_id)`) are right without a service filter. (AC1)
- **S2** — `rubato.hook.forwarded` is labelled by `rubato.hook_event` and `rubato.companion_id` only. The session id stays on the `rubato.hook.forward` span around each forward. (AC2)
- **S3** — `observability/check.ts` rejects a rule or panel that queries `rubato_hook_forwarded_total` by `rubato_session_id`, a label the counter no longer carries. Its comment on the `max by` rule says why it stays: a companion built before this change still exports its own copy until it is upgraded.
- **S4** — The end-to-end run checks that the companion's OTLP metrics carry neither `rubato.sessions.by_state` nor `rubato.session_id`, and logs how many names it checked.
- **S5** — `crates/rubato-protocol/src/otel.rs` documents which binary records each of the two metrics and with which labels.

## 4. Caveats triage

- Telemetry names: no name changes. One instrument leaves the companion; one attribute leaves one counter. Alerts and dashboards checked by `observability/check.ts` (6 rules, 13 rule tests, 30 panels) and promtool.
- Contract compatibility: no protocol type or schema change. A companion built before this change still exports its own `rubato.sessions.by_state` until it is upgraded; the Hooks/min panel keeps `max by` for that window, and the "Sessions by state" sum is high by that companion's sessions until then. One team, a handful of machines.
- Cardinality: `rubato.hook.forwarded` drops from one series per session and event to one per companion and event. `rubato.hook_event` comes from Claude Code's event names, a small set.
- Gauge staleness: the server's gauge keeps its last value for a companion that disconnects, so "Sessions by state" can show *working* for a companion with no heartbeat. This is existing behaviour (the server recorded the gauge before this change too), and it now matters more because the server is the only source. `SessionWorkingNoHooks` is safe, because the `and` is empty once the hook series goes stale, and `CompanionSilent` pages. Zeroing on disconnect was tried and dropped: the companion sends a snapshot only when it changes, so a reconnect with no change would leave the gauge at zero. Filed as #69.
- n/a: Boundaries, Concurrency, Schema change, Idempotency, Authorisation, Cost, Derived not stored, Own tmux only, Log level.

## 7. Decisions

- **D1** — the server owns `rubato.sessions.by_state` · because AGENTS.md ("What each part emits") already lists sessions by state under `rubato-server`, the server sees every companion's snapshot, and one source makes every sum right without a filter each panel and rule must remember · rejected: companion only (the alert would then depend on the companion's export for both of its sides, and AGENTS.md says otherwise); both sides with a service filter enforced by `check.ts` (every new query still has to know about it, and Prometheus label names for the service depend on the collector).
- **D2** — session id on the span only · because the per-companion hook rate is what the alert and panel use, and a series per session grows without bound; Tempo answers "which session stopped" · rejected: keeping it on the counter.
