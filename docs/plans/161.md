# Revoking a pairing closes the companion websocket

Revoking a pairing marks the row revoked and drops the server's sender for that companion, but
the companion socket loop keeps reading: the `rx.recv()` arm just stops matching
(`crates/rubato-server/src/companion_link/ws.rs:91-123`) and `on_envelope` never looks at the
pairing again (`ws.rs:110`). A revoked companion (a lost laptop, a leaked token) keeps posting
session snapshots and cap hits for as long as it holds the socket. This change makes revocation
end the socket and makes every envelope prove the pairing is still live before anything is
stored. Design: [161-revoke-closes-socket/design.md](161-revoke-closes-socket/design.md).

## What the change does

- **S1** — When a user revokes a pairing whose companion is connected, the companion receives the `Error { code: "auth", message: "pairing revoked" }` it already gets, then a websocket Close, and the server ends the connection.
- **S2** — An envelope that arrives on a socket whose pairing is revoked (or whose token no longer matches the pairing, after a re-pair) is not recorded, not stored and not fanned out; the server answers `Error { code: "auth" }`, closes the socket and counts the envelope in `rubato.events.dropped` with `rubato.reason = "revoked"`.
- **S3** — When the same companion connects a second time, the older socket is closed and the newer one keeps receiving launches; the older socket's exit no longer removes the newer connection from the server's table.

## How we'll know it works

- [x] `a_revoked_companion_is_disconnected_and_stores_nothing` (integration): connect, hello, revoke over HTTP; the socket yields the `auth` error and then closes; a `Sessions` envelope sent afterwards is not in `session_snapshots`. Fails today: the socket stays open (proves S1).
- [x] `an_envelope_after_revocation_is_dropped` (integration): connect, hello, set `revoked_at` in the database without touching the in-memory sender, send `Sessions`; the reply is `Error { auth }`, the socket closes, and neither a snapshot nor the event is recorded. Fails today: the reply is `Ack` and the snapshot is stored (proves S2).
- [x] `a_revoked_envelope_is_counted_as_dropped_revoked` (unit, `ws.rs`): the refusal adds 1 to `rubato.events.dropped{rubato.reason="revoked"}` (proves the S2 signal; integration tests cannot read the meter).
- [x] `a_second_connection_replaces_the_first` (integration): connect twice with one token; the first socket closes; a launch reaches the second socket. Fails without the connection id: the first socket's exit removes the second's entry, which drops its sender and closes the second socket too (proves S3).

## What it must not break

- **N1** — A live pairing's envelopes are recorded, acknowledged and replayed exactly as before: `protocol_fixtures_replay_derives_progress`, `welcome_carries_last_seen_seq_after_reconnect`, `a_replayed_hello_is_counted_and_a_higher_one_is_welcomed`.
- **N2** — Bad and revoked tokens are still refused at upgrade: `bad_and_revoked_tokens_are_refused`.
- **N3** — Launches still reach only the caller's own connected companion: `launch_goes_only_to_the_callers_own_connected_companion`.
- **N4** — The web sees the companion as disconnected after revoke (`connected` from the companions table) and gets a `Changed` event: `web_events_follow_every_action`.

## How we'll debug it at 3 am

See the O-rows. New log lines, both on the companion socket span `rubato.inbound_event` or its
connection: `warn` "envelope from a revoked pairing dropped" with `rubato.companion_id` and `seq`,
and `info` "companion disconnected" with `reason` (`sender_dropped` after a revoke or a newer connection, `revoked` from the re-check, `closed` by the companion or the network). A companion
that keeps being disconnected shows as a rising `revoked` series on the Events dropped panel.

## Tasks

1. Write the three integration tests in `crates/rubato-server/tests/integration.rs`; run them and see each fail for the reason given above.
2. `kernel/state.rs`: `CompanionConn` gains `conn: Uuid`. `companion_link/ws.rs`: pass the token into `handle`; insert with a fresh `conn`; break and close when `rx.recv()` returns `None`; remove the entry on exit only when its `conn` is ours.
3. `companion_link/ws.rs`: before `on_envelope`, re-read the pairing with `pairing::authenticate(token)`; when it is missing, revoked or names another companion, count `events_dropped{reason=revoked}`, log, send `Error { auth }`, close and break. Use the fresh row for `on_envelope`.
4. `cargo fmt --all`, `cargo clippy -p rubato-server --all-targets -- -D warnings`, `cargo test -p rubato-server`.

## Assumed, not yet approved

| # | Decision | Chosen | Alternatives | Scope |
| --- | --- | --- | --- | --- |
| A1 | When to re-check the pairing | on every inbound envelope (one indexed SELECT on `token_hash`) | a timer; only on `rx` closing | node |
| A2 | A database error during the re-check | fail closed: drop the envelope and close; the companion reconnects and replays its outbox | fail open and store | node |
| A3 | A second connection for the same companion | the newer one wins, the older socket is closed | refuse the newer one | node |
| A4 | Drop reason name | `revoked`, a new value of `rubato.reason` on `rubato.events.dropped` | reuse `auth` | node |
