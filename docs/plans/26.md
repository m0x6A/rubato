# Companion telemetry attributes match the alerts

Issue: #26 · Track: small · Branch: `issue/26-telemetry-attributes`

## 1. Problem

Found while designing #20 (design §11). The companion's metrics lack the attributes the alert
rules and dashboard group by, so one "never silent" alert cannot fire and two panels show one
undivided series.

**Acceptance criteria** (from the issue)

- [ ] **AC1** — `rubato.sessions.by_state` and `rubato.hook.forwarded` from the companion carry `rubato.companion_id`, so `SessionWorkingNoHooks` can fire.
- [ ] **AC2** — `rubato.sessions.discovered` carries `rubato.session.source`, which the "Sessions discovered" panel splits by.
- [ ] **AC3** — `rubato.issues.by_state` uses a `rubato.*` attribute instead of a bare `state` key.
- [ ] **AC4** — the declared spans `rubato.hook.forward` and `rubato.team_poll` are emitted.

Prior art: `docs/plans/20-vertical-slices/design.md` §9 (Observability row) and §11.

## 2. Spec

### 2.1 What the change does

- **S1** — When the companion records `rubato.hook.forwarded` or `rubato.sessions.by_state`, the data point carries `rubato.companion_id`. (AC1)
- **S5** — When either binary records `rubato.sessions.by_state`, it records every session status, 0 included (the companion on each reconcile, the server per companion on each `Sessions` snapshot). A gauge keeps its last value, so without the zero a session that stops working would leave `working` at 1 and `SessionWorkingNoHooks`, which can fire after S1, would page on every finished turn.
- **S6** — When the companion starts, it records `rubato.hook.forwarded` with 0 and its `rubato.companion_id`, so the series exists before the first hook: after a companion restart, sessions launched earlier post to a dead port, and without the seed the alert's hook side would be empty and the alert silent in exactly that case.
- **S7** — When `tmux-ide team --json` fails, the `rubato.team_poll` span records the error and the companion logs `warn!` on the first failure and `info!` on recovery (today every failure is `debug`, below the default filter).
- **S2** — When the companion reconciles, it records `rubato.sessions.discovered` once per source (`hook`, `tmux_ide`, `launch`, `scraped`; the protocol's snake_case names) with `rubato.session.source` and `rubato.companion_id`, including a 0 for a source with no session, so a source that empties does not keep its last value. (AC2)
- **S3** — When the server refreshes its gauges, `rubato.issues.by_state` carries the state under `rubato.issue.state` (new constant `attr::ISSUE_STATE`); the "Issues by state" panel groups by `rubato_issue_state`. (AC3)
- **S4** — When the companion forwards a hook it does so inside a `rubato.hook.forward` span with `rubato.session_id` and `rubato.hook_event`; each `tmux-ide team --json` poll runs inside a `rubato.team_poll` span. (AC4)

## 3. Where it changes

- `rubato-protocol` — `src/otel.rs`: `attr::ISSUE_STATE = "rubato.issue.state"`, added to `all_names`.
- `rubato-companion` — `src/hooks/arm.rs`: companion id on `hook_forwarded`; `rubato.hook.forward` span. `src/sessions/tasks.rs`: companion id on `sessions_by_state`; `sessions_discovered` per source; `rubato.team_poll` span. `src/sessions/registry.rs`: `counts_by_source`. `src/runtime.rs`: passes the companion id.
- `rubato-server` — `src/overview/gauges.rs`: `attr::ISSUE_STATE` instead of `"state"`. `src/companion_link/ws.rs`: every session status recorded per snapshot, zero included.

## 4. Caveats triage

- Contract compatibility: the label on `rubato_issues_by_state` is renamed (`state` → `rubato_issue_state`). The only consumer is the dashboard in this repo (grep of `observability/`: one expression, `rubato-overview.json:254`; no alert uses it), changed in the same PR.
- Observability: this change is observability; O1, O2.
- Telemetry names (project): all names from `otel.rs`; alerts unchanged; one dashboard expression changed.
- Check reports its count (project): the e2e prints `saw N/N attribute keys per binary` and `saw N/N span names`; `check.ts` gains a must-fail case in its own test input (a dashboard grouping by `state`).
- Log level (project): spans are `info`, exported under the default filter.
- Testability: OTLP bodies are protobuf with the strings in clear; the e2e receiver already keys names by `service.name`.
- n/a: Boundaries, Idempotency, Concurrency, Schema change, Authorisation, Cost, Seam O-row beyond the table above, Derived not stored, Own tmux only — telemetry attributes only; no handler, table, entry point or launch path changes.

## 7. Decisions

- **D1** — zero is recorded for an empty source · because a gauge keeps its last value, so a source that empties would otherwise look populated · rejected: recording only non-empty sources.
- Override: three deployables change (full-track trigger) — the person kept it small on 2026-11-10: the protocol change is one additive telemetry constant with no schema or seam change.

## Review outcome

design-reviewer, 2026-11-10: 3 blockers; all taken.

- **Spec check:** Does: ok. We'll know it works: gap (nothing could fail for S1: the heartbeat already carries the companion id in the same body). Must not break: missing the server's own `sessions.by_state` site and the "Hooks/min vs working sessions" panel, whose working line would double. Debug at 3 am: gap (the alert stays silent after a companion restart; a failing team poll is logged at `debug`).
- **Track check:** small holds: no migration, wire schema, consumer, boundary, dependency or auth change. Accepted risk, reported once: three deployables change (§7 Override).
- **Fixed:** zeros for every session status on both binaries (S5), or the alert would page on every finished turn; in-memory metric tests for the companion id (S1); a seeded hook counter (S6) and two promtool cases; team poll failures visible (S7); panel uses `max by` (N6); source values in the protocol's snake_case.
- Not in scope, noted by the reviewer: `rubato.hook.forwarded` keeps `rubato.session_id` as a metric attribute, one series per session ever seen. Predates this change; worth its own issue.
