# Publish the dashboard and alert rules to Grafana on merge

Issue: #57 · Track: small · Branch: `issue/57-publish-observability`

## 1. Problem

`observability/dashboards/rubato-overview.json` and `observability/alerts/rubato.rules.yml` are
code and are checked in CI, but nothing sends them to the Grafana stack. A panel or rule added
in a pull request exists only in the file until someone imports it by hand. Sagly publishes on
merge; Rubato does not.

**Acceptance criteria** (from the issue)

- [x] **AC1** — a merge to `main` that changes `observability/` publishes the dashboard and the alert rules.
- [x] **AC2** — the publisher reports how many dashboards, panels and rules it published and reads them back to confirm.
- [x] **AC3** — a missing setting, an unknown datasource or a refused call fails the run and names what is wrong.
- [x] **AC4** — a dry run shows what would be sent without writing.
- [x] **AC5** — no Python; the alert rules stay in Prometheus format, so the promtool tests keep testing what runs.

Prior art: sagly's `publish-telemetry.yml` and its Python publishers. Kept: publish on merge, the
folder found by title, the read-back, the advisory live check, no cancelling part-way. Changed:
Node instead of Python (AGENTS.md); the rules are not rewritten into Grafana's own rule format.

## 2. Spec

### 2.1 What the change does

- **S1** — When a push to `main` changes `observability/**` or the workflow, the workflow runs the structural check and its tests, then `observability/publish.ts`. (AC1)
- **S2** — The publisher writes every `dashboards/*.json` into the folder "Rubato" with overwrite, after replacing `${DS_PROMETHEUS}` and `${DS_LOKI}` with the uids of the datasources named by `GRAFANA_PROM_DS` and `GRAFANA_LOKI_DS`. The folder is the root folder titled exactly "Rubato", found by title and made only when absent. (AC1)
- **S3** — The publisher sends each group of `alerts/*.rules.yml` unchanged to `POST /api/convert/prometheus/config/v1/rules/Rubato`, with the metrics datasource in a header. Grafana finds the root folder titled "Rubato" (the namespace) and keeps the group there as Grafana-managed rules. No parent-folder header is sent, since it would nest a second "Rubato" inside the first. Sending a group replaces it. With `GRAFANA_ALERTS_PAUSED=true` the rules arrive paused. (AC1, AC5)
- **S4** — After each write it reads the dashboard and the group back and fails when the panel or rule count differs from what it sent. It prints one line with the counts. (AC2)
- **S5** — Before the first write it fails, naming the cause, on: a setting that is unset or blank; a datasource name the stack does not have; a datasource placeholder it cannot resolve; a dashboard without a uid; a rules file without groups. A refused call, a 404 anywhere but the datasource lookup, and an answer that does not parse each fail with the method and path; a refusal also carries the status and Grafana's answer, never the token. (AC3)
- **S6** — `--dry-run` makes the same reads and no write, prints the same counts, and says when a publish would make the folder. (AC4)
- **S7** — `--verify-live` lists the metric names the files query that the stack has never stored. It exits 0 when it could ask, and fails when the stack gives no list of names; the workflow runs it with `continue-on-error`.

### 2.2 How we'll know it works

| Proves | Evidence | Kind |
|---|---|---|
| S2, S3, S4, AC1, AC2 | `publish.test.ts` "publishes the committed dashboard and rules, reads them back, and reports the counts" against a stand-in for the HTTP API | unit |
| S2 | "an existing folder is reused, whatever its uid"; "publishing twice leaves one dashboard and one group" | unit |
| S5, AC3 | nine must-fail tests: missing settings, unknown datasource, refused call, short dashboard read-back, short rules read-back, unresolved placeholder, no uid and no groups, a 404 or unparseable answer, verify-live without a list | unit |
| S6, AC4 | "a dry run reads but writes nothing"; `pnpm observability:publish --dry-run` against the real stack on 2026-11-11: 1 dashboard, 31 panels, 6 rules, nothing written | unit, manual |
| S7 | "verify-live lists the metrics the stack has never stored"; run against the real stack: 27 names queried | unit, manual |
| S1, S3 against the real API | the first run of the workflow after merge. **Not verified before merge:** no write has been made to the stack. The stand-in encodes my reading of the import route (namespace is a root folder title, one group per POST, 202, read back per namespace), taken from Grafana's migration guide and the handler source on `main`, not from Grafana 13.4 itself. If the reading is wrong the run goes red at the read-back, after the write | production |

### 2.3 What it must not break

| # | Must keep working | Guarded by |
|---|---|---|
| N1 | Sagly's and PantryPilot's folders, dashboards and rules on the same stack | by construction, not by a test that can see their content: the publisher writes only the folder "Rubato", dashboards by their own uid, and the rule namespace "Rubato"; the first test asserts those three paths |
| N5 | Nobody is paged by a rule that fires only because no server exports yet | the stack's root notification policy is shared and has an empty receiver today; `GRAFANA_ALERTS_PAUSED=true` is set on the repository, so the rules arrive paused until someone removes it |
| N6 | A branch never reaches the stack | the job runs only when `github.ref` is `refs/heads/main`, also when started by hand |
| N2 | The rules promtool tests are the rules that run | S3 sends the parsed group unchanged; the test compares it with the file |
| N3 | CI | `observability:test` now also runs `publish.test.ts`; no new CI step |
| N4 | The token | sent only in the `Authorization` header to `GRAFANA_URL`; given to the two steps that call Grafana, not to the install or the tests; the refused-call test asserts it is not in the error |

### 2.4 How we'll debug it at 3 am

| # | When this fails | How we find out | What localises it | First action |
|---|---|---|---|---|
| O1 | The publish run fails | the workflow run is red on the merge commit | the line `observability publish failed: <METHOD> <path> answered <status>: <answer>`, or `missing setting(s): …` | 401/403: the token or its permissions; 404 on a datasource: the variable; fix and re-run with workflow_dispatch |
| O2 | A panel shows No data after a publish | the panel | the "never stored" list of the `--verify-live` step in the same run | the query names a series nothing emits, or no server exports to this stack |
| O3 | A run stops between the dashboard and the rules | red run | the last `dashboard …` or `rule group …` line printed before the error | re-run; every write is an overwrite, so a second run is safe |

## 4. Caveats triage

- Idempotency: every write is an overwrite keyed by dashboard uid or group name; tested by publishing twice.
- Shared stack: N1. Rubato's metrics are all `rubato_*` or carry `rubato_*` labels, so no extra scoping label is added.
- Check reports its count: the publish line and the two test lines print counts; seven must-fail tests.
- Removal: a rule removed from a group leaves the stack with the next publish. A removed group or dashboard does not (A2).
- n/a: migrations, wire schemas, authorisation in Rubato, derived state, tmux.

## 7. Decisions

- **D1** — send the Prometheus rules to Grafana's import route · because the file promtool tests is then the file that runs, with no second format to keep in step · rejected: rewriting each rule as a Grafana provisioning rule, as sagly does.
- **D2** — the URL and the datasource names are repository variables, the token is a secret · because only the token is secret, and a variable can be read back.
- **Override:** a new external dependency (Grafana's HTTP API, including the import route only Grafana has) would call for the full track. Kept small because it is used only by one script in CI, nothing at runtime depends on it, and the dashboard and rule files stay vendor-neutral.

## Review outcome

design-reviewer, 2026-11-11: 1 blocker, 4 should-fix, 2 nits; all taken.

- **Spec check:** Does: ok. We'll know it works: gap (the import route is proven only against a stand-in that holds the publisher's own reading). Must not break: gap (N1 could not be seen by its test; the shared notification policy was missing). Debug at 3 am: gap (a 404 or an unparseable answer lost the path; nobody is named to be woken).
- **Track check:** small holds for the code; one trigger, the new external dependency, now has an Override line in §7.
- **Fixed:** the parent-folder header is gone, so the rules land in "Rubato" and not "Rubato/Rubato", and the folder is matched by exact title; the job runs only on `main`; rules can arrive paused (N5); only the datasource lookup may answer 404, and parse failures name the call; the token is step-level; `metricNames` skips non-Prometheus panels, `offset` durations, numbers like `1e3` and one-argument `label_values`; the dry run says when it would make the folder.
- **Left open:** the import route is unproven against the real stack until the first run (§2.2); who is woken when a rule fires (A3).
