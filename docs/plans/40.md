# Companion: launches on their own task, and a timeout on git, tmux-ide and tmux

Issue: #40 · Track: full (a new task loop in the runtime; one deployable, no migration or
contract change, so design and tasks are kept in this one file) · Branch: `issue/40-launch-task`

## 1. Problem

After #27 the registry lock is free during a launch, but the dispatch loop
(`crates/rubato-companion/src/runtime.rs` `Dispatch::run`) still awaited `launch::on_command`, so
hook events queued until the launch returned. The adapters in `kernel/` (`gitx::git`,
`TmuxIde::run`, `Tmux::run`) called `Command::output()` with no bound, so a `git fetch` or a
`tmux-ide` call that hung stopped hook forwarding for every session on the machine for as long as
it hung. Left out of #27 on purpose (plan 27 D2).

**Acceptance criteria** (from the issue)

- [x] **AC1** — launches run on their own task; hook events are applied and forwarded while a launch runs. One launch at a time is still fine.
- [x] **AC2** — the external commands a launch runs have a timeout; when it is hit the launch is reported as `Failed`.

## 2. Spec

### 2.1 What the change does

- **S1** — The runtime starts an essential `launch` task (`launch::run`) that reads launch commands from a channel and handles them one at a time with `launch::on_command`. The dispatch loop only forwards `ServerMessage::Launch` into that channel, so a hook event that arrives during a launch is applied and forwarded without waiting for it. (A hook from a session the registry does not know yet still runs `identify` under the registry lock, as before this change; see §7 D3.) (AC1)
- **S2** — Every external command the companion runs and waits for (git, tmux-ide, tmux) goes through one kernel helper, `kernel::proc::output`, with a deadline. The command runs as its own process-group leader. When the deadline passes, the helper sends TERM to the whole group, then KILL after 2 s, reaps the leader and returns a `TimedOut` error naming the command, its working directory and the timeout. `tmux-ide events --follow` is long-lived on purpose and stays outside the helper. (AC2)
- **S3** — Timeouts: the launch's `git fetch` and every `tmux-ide` call use `companion.command_timeout_secs` from `workspace.yml` (default 120; `0` is refused at parse time, naming the key). `tmux-ide team --json`, which reconcile waits for every cycle, uses at most 30 s. Local git calls (`rev-parse`, `worktree list`, `remote get-url`) and tmux calls use a fixed 30 s. (AC2)
- **S4** — A launch whose command times out ends as `LaunchResult::Failed` with the error text. That includes a timeout on the `tmux-ide --version` check, which otherwise turns every error into `Refused { missing_dependency }`; a timeout is not a missing dependency. A version check that fails for any other reason is still `missing_dependency`. (AC2)
- **S5** — When a command times out, the companion logs `warn!(command, cwd, timeout_secs, "external command timed out")`, so a hung tool has a line that names it.
- **S6** — When a hook from the launched session (its `session_id` is the command's) is applied before the launch is recorded, `apply_launch` upgrades that entry in place. It keeps the hook's status, source, last seen and transcript, and adds the pane, tmux session, worktree, branch, issue, launch id and spend cap. That holds also when reconcile has meanwhile matched the hook-only entry to the new pane by cwd. There is never a second entry for one session id, and nothing is retired.
- **S7** — A tmux probe that times out (`server_running`, `has_session`) is an error, not a "no". `panes()` returns `Err`, so reconcile takes its existing `tmux list-panes failed` arm and keeps its entries, instead of reading "no server" and ending every session on the machine. A tmux that cannot start, or a server that is not running, still reads as "no".

## 4. Caveats triage

- Concurrency: hooks and the launch now interleave. Three things can run between `begin_launch` and `apply_launch`: reconcile (handled in #27 by `begin_launch`), the stale sweep (unchanged), and now hook events. A hook from an unrelated session touches only its own entry. A hook from the launched session is S6, including the case where reconcile has given that hook-only entry the new pane. Launch commands stay serialised by the single launch task (N2).
- Idempotency: a replayed launch command is still refused as `already_running` once the first is recorded; while the first is in flight the second waits on the channel, as before.
- Timeouts and process groups: the helper puts the child in its own process group (`CommandExt::process_group(0)`) and signals the group with `kill -TERM -- -<pgid>`, then `kill -KILL` (no `libc` dependency). A tmux server started by `tmux new-session` daemonises (`setsid`, stdio to `/dev/null`), so it leaves that group and is not signalled by a later timeout. Ctrl-C at a terminal no longer reaches these children, but the companion is a daemon and they are short-lived.
- What a timeout leaves behind: a fetch that ignored TERM can leave a `*.lock` in the developer's clone; a killed `tmux-ide worktree create` can leave a registered, partial worktree that the retry reuses. Neither is cleaned up automatically; O4 says how to find and clear it.
- Output pipes: after the child exits, a grandchild could still hold its stdout open (the old `output()` would have blocked on it forever); the helper waits for the pipes only until the same deadline, then counts it as a timeout.
- Observability: O1, O2, O4 are new lines; O3 is a new task name under the existing event.
- n/a: Schema change (an optional `workspace.yml` key with a default, companion-only), Contract compatibility (no protocol change), Authorisation, Cost, Telemetry names (no new `rubato.*` name; the log message is plain text), Derived not stored, Check reports its count, Boundaries (kernel helper, used by kernel adapters only).

## 7. Decisions

- **D1** — one synchronous kernel helper with a deadline, not `tokio::process` with `tokio::time::timeout` · because the launcher runs inside `spawn_blocking` and the adapters are called from blocking code elsewhere too · rejected: making the adapters async (touches every caller in four slices).
- **D2** — signal the process group, TERM then KILL · because a `sh` wrapper (the stand-ins; tmux-ide is a Node program that spawns tmux) would leave its children holding the output pipe, and git cleans its lock files only on a catchable signal · rejected: `Child::kill` alone.
- **D3** — `identify` for an unknown session's first hook still runs git under the registry lock, on the dispatch loop · because that is unchanged behaviour shared with reconcile, and moving it out of the lock changes `apply_hook`'s shape in the hooks slice · rejected for this change: computing identity in `spawn_blocking` before taking the lock. Each git call there is now bounded at 30 s instead of unbounded. Worth its own issue if hooks are seen stalling.
