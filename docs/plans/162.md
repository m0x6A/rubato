# The server takes a companion's identity from its pairing, not its messages

The server trusts identity fields a companion writes into its own messages. Each
`SessionState.companion_id` and `.user` in a `Sessions` snapshot is stored as sent
(`crates/rubato-server/src/companion_link/ws.rs:241-248`), and the web groups lanes by that claim
(`web/src/features/companions/Lanes.tsx:257`). A `CapHit` is stored for any issue
(`ws.rs:275-279`, `launch/store.rs:101-110`) and a live one makes the issue Blocked
(`crates/rubato-protocol/src/progress.rs:131-133`). A `LaunchResult` updates `launches` by command
id alone (`launch/store.rs:24-37`). So A's companion can show made-up sessions in B's lane under
B's name, and can turn any teammate's issue Blocked. This change makes the pairing the only source
of a companion's identity. Design: [162-companion-identity/design.md](162-companion-identity/design.md).

## What the change does

- **S1** — Every session in a `Sessions` snapshot is stored with the pairing's `companion_id` and `user`, whatever the companion wrote. A snapshot whose claims differed logs one `warn` "session identity overwritten" with the number of sessions changed.
- **S2** — A `CapHit` is stored only when this companion has a launch for the issue, or a session on it in its stored snapshot (repo compared without case). Any other cap hit is acknowledged, not stored, not fanned out, and counted in `rubato.events.dropped` with `rubato.reason = "identity"`; the issue's progress is unchanged.
- **S3** — A `LaunchResult` updates a launch only when that launch was sent to this companion. A result naming another companion's command changes nothing, settles no queue entry, and is counted as `rubato.reason = "identity"`.
- **S4** — A `Stale` event is recorded under the pairing's companion id, not the one it names.

## How we'll know it works

- [x] `a_snapshot_cannot_claim_another_companion_or_user` (integration): A and B are paired; A sends a snapshot whose session names B's companion id and user `bob`; A's stored snapshot holds the sessions under A's companion id and user, and no session in the overview names B's companion. Fails today: the stored sessions keep B's id and `bob` (proves S1).
- [x] `a_cap_hit_for_an_issue_this_companion_does_not_run_is_dropped` (integration): B's issue is pinned and launched on B's companion; A sends a `CapHit` for it; the reply is `Ack`, `cap_hits` has no row and the issue is not Blocked. Then B sends the same hit and the issue is Blocked. Fails today: A's hit blocks it (proves S2).
- [x] `a_launch_result_for_another_companions_command_changes_nothing` (integration): a launch goes to B; A sends `Started` with that command id; the launch row has no result and the issue is not Started. Fails today: the row takes A's result (proves S3).
- [x] `a_foreign_identity_envelope_is_counted_as_dropped_identity` (unit, `ws.rs`): the refusal adds 1 to `rubato.events.dropped{rubato.reason="identity"}` (proves the S2 and S3 signal; integration tests cannot read the meter).
- [x] `a_stale_event_is_recorded_under_the_pairing` (integration): A sends `Stale` naming B's companion id; `stale_events` has the row under A (proves S4).
- [x] `own_sessions_counts_only_the_claims_it_changed` (unit, `ws.rs`): the overwrite counts only sessions whose claim differed, for the `overwritten` field of the log line (proves the S1 signal).

## What it must not break

- **N1** — An honest companion's snapshots, cap hits and launch results behave as before: `protocol_fixtures_replay_derives_progress` (its cap hit on #2 now comes after a session on #2, which is what a real companion sends), `attempt_limit_blocks_the_issue_and_is_an_event`, `a_spend_hit_blocks_whatever_the_companion_clock_says`, `a_spend_hit_blocks_after_a_second_start_was_refused_as_already_running`, `a_companion_attempts_hit_blocks_whatever_the_companion_clock_says`, `queue_entry_leaves_on_started_and_stays_on_refused`.
- **N2** — Spend history stays keyed by the pairing: the existing `spend_history` tests.
- **N3** — Every accepted envelope still gets its `Ack`, so the companion's outbox drains: `web_events_follow_every_action`, `welcome_carries_last_seen_seq_after_reconnect`.
- **N4** — A repo spelled differently by the remote still joins: `a_remote_spelled_differently_takes_the_maps_spelling`; the cap-hit check compares repos without case.

## How we'll debug it at 3 am

See the O-rows. New signals: `rubato.events.dropped{rubato.reason="identity"}` with `warn`
"cap hit for an issue this companion does not run dropped" (`rubato.companion_id`,
`rubato.issue`) and "launch result for a command not sent to this companion" (`rubato.companion_id`,
`rubato.launch_id`); `warn` "session identity overwritten" (`rubato.companion_id`, `overwritten`).
An honest companion that starts tripping `identity` points at a launch row written under another
companion id, or at a cap hit sent before any launch.

## Data flow

```mermaid
sequenceDiagram
  participant C as rubato-companion (A)
  participant S as rubato-server
  C->>S: Sessions [ {companion_id: B, user: bob, ...} ]
  S->>S: companion_id := A, user := pairing(A).user; store
  C->>S: CapHit { issue: B's issue }
  S->>S: launch or session on A for that issue? no
  S-->>C: Ack (dropped, rubato.reason=identity)
  C->>S: LaunchResult { command_id: B's launch }
  S->>S: UPDATE launches ... AND companion_id = A: 0 rows
  S-->>C: Ack (dropped, rubato.reason=identity)
```
