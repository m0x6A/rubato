# Companion launch arm: no block_in_place under the registry lock

Issue: #27 · Track: small · Branch: `issue/27-launch-without-lock`

## 1. Problem

`launch::on_command` (`crates/rubato-companion/src/launch/arm.rs:19-24`) holds the registry mutex
across `tokio::task::block_in_place(Launcher::handle)`, which runs `git fetch`, `tmux-ide` and
`tmux`. Hooks and reconcile wait for the whole launch, and `block_in_place` panics on a
current-thread runtime. Moved as is in #20.

**Acceptance criteria** (from the issue)

- [ ] **AC1** — the launch does not hold the registry lock while it runs git, tmux-ide or tmux.
- [ ] **AC2** — the launch arm does not use `block_in_place`.

Prior art: design #20 §9.1 (launch arm order) and §11.

## 2. Spec

### 2.1 What the change does

- **S1** — When a launch command arrives, the companion reads what it needs from the registry (is a live session already running for this issue) under the lock, releases it, and only then runs the launch; reconcile and the stale sweep, which take the same lock, proceed during a slow launch. Hooks are still applied only after the launch returns: the dispatch loop that applies them is the one awaiting the launch (`runtime.rs` `Dispatch::run`). Unblocking hooks needs launches on their own task and is out of scope (§7 D2). (AC1)
- **S3** — When reconcile sees the new pane before the launch is recorded (possible now that the lock is free during the launch), `apply_launch` upgrades that entry in place instead of ending it and adding a second one, so the server never sees a phantom session for the issue.
- **S4** — When the blocking work starts, the companion logs `info!(launch_id, issue, "launch started")`, so a hung launch has a line that names it.
- **S2** — When the launch arm runs on a current-thread runtime, it completes instead of panicking: the blocking work runs in `spawn_blocking`. (AC2)

### 2.2 How we'll know it works

| Proves | Evidence | Kind |
|---|---|---|
| S1, AC1 | `launch::arm::tests::registry_is_free_during_a_slow_launch`: a stand-in `tmux-ide` writes a marker file, sleeps 1 s, then prints version `0.0.1` (so the launch is refused as `missing_dependency` and needs no tmux server); a spawned probe waits for the marker and only then calls `registry.try_lock()`, which must succeed within 200 ms; `multi_thread, worker_threads = 2` | unit |
| S2, AC2 | `launch::arm::tests::runs_on_a_current_thread_runtime`: the same stand-in and the paired user on `flavor = "current_thread"`; the `Refused { reason: MissingDependency }` result is read from the `out` receiver, so the path goes through the blocking closure | unit |
| S3 | `launch::apply::tests::a_pane_discovered_before_the_launch_is_recorded_is_upgraded`: `apply_panes` with the new pane, then `apply_launch`; exactly one live entry for the pane, with the launch's session id and `source: Launch`, and no `Ended` entry | unit |
| S4 | the S1 test captures the log and finds `launch started` with the `launch_id` before the result | unit |

### 2.4 How we'll debug it at 3 am

| # | When this fails | How we find out | What localises it | What it tells us · first action |
|---|---|---|---|---|
| O1 | The blocking launch task panics or is cancelled | the server shows the launch as failed: the arm sends `LaunchResult::Failed` with the join error; `info!(launch_id, issue, outcome, "rubato.launch")` on the companion | `launch_id` and `issue` on that line | the launcher crashed mid-launch · read the error, check the worktree and tmux session by hand |

## 3. Where it changes

- `rubato-companion` — `src/launch/launcher.rs`: `Launcher` owns its fields (cloned once at start) so it can move into `spawn_blocking`; `handle` takes the live-session answer instead of `&Registry`. `src/launch/arm.rs`: lock → read → unlock → `spawn_blocking`. `src/launch/apply.rs`: `live_for_issue` result described as an owned value. `src/runtime.rs`: builds the owned launcher.

## 4. Caveats triage

- Concurrency: the registry is one `tokio::sync::Mutex`. Launch commands are serialised by the dispatch loop (N4), and hooks cannot interleave with a launch for the same reason. What can now run between the check and `apply_launch` is reconcile: the launch adopts the new session in tmux-ide, the events watcher wakes reconcile, and reconcile adds an entry for the new pane (`sessions/discovery.rs`) and sends a snapshot. Before this change the lock was held through that window. S3 handles it: `apply_launch` upgrades an entry on the same pane that has no session id and sits in the launch's worktree; an entry with a session id or another cwd is still retired as before.
- Idempotency: a replayed launch command for a running issue is still refused as `already_running` (N2).
- Observability: O1 is new (a join error becomes a `Failed` result instead of a panic in the dispatch loop).
- Testability: the slow stand-in for `tmux-ide` is a shell script; the launcher is refused or fails after it, so no tmux server is needed for the unit tests.
- n/a: Boundaries, Schema change, Contract compatibility, Authorisation, Cost, Telemetry names, Derived not stored, Check reports its count, Log level — one slice of one deployable; no message, table, name or check changes.

## 7. Decisions

- **D1** — `spawn_blocking` with an owned launcher · because it works on any runtime and frees the dispatch task's worker thread · rejected: keeping `block_in_place` and only moving the lock (still panics on a current-thread runtime).

- **D2** — hooks still wait for a launch · because applying hooks during a launch needs launches on their own task, a new loop in the runtime (a full-track trigger) · rejected for this change: a dedicated launch task reading commands one at a time. Worth its own issue; a timeout on `git fetch` and tmux-ide belongs there too.
