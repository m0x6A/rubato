# Companion: emit CapHit for the attempt limit

Issue: #30 · Track: small · Branch: `issue/30-attempt-cap-hit`

## 1. Problem

`CapKind::Attempts` exists in the protocol but nothing sends it. The server refuses a launch past
`attempt_limit` with a 409 before the companion sees it (`crates/rubato-server/src/launch/handler.rs:107`),
and that refusal is not a cap-hit event, so the issue never shows *Blocked*. AGENTS.md ("Cost is a
signal"): every launch carries a spend cap and an attempt limit; when either is hit the issue is
marked *Blocked*, "and that is an event, not a log line".

**Acceptance criteria** (from the issue)

- [ ] **AC1** — hitting the attempt limit produces a `CapHit` with kind `attempts`.

Prior art: design #20 §11; the spend-cap path (`crates/rubato-companion/src/spend/arm.rs`) is the model.

## 2. Spec

### 2.1 What the change does

- **S1** — When a user starts a session on an issue whose attempts are used up, the server still answers 409, and now also logs the `rubato.cap.hit` event with the issue (before the write), records a cap hit (kind `attempts`, value = the attempt asked for, limit = the limit) and notifies browsers. If no session is live for the issue, its derived state becomes *Blocked*. (AC1)
- **S4** — When the issue still has a live session (someone presses *Start* again during a run; a running launch counts toward the limit), the refusal is still an event, but the derived state stays what the session says: an `attempts` hit does not block while a session for the issue is live. A `spend` hit blocks as before.
- **S5** — When storing the cap hit fails, the server logs `error!(slice = "launch", rubato.issue, error, "storing cap hit")` and still answers 409.
- **S2** — When the companion itself refuses a launch command as `attempt_limit_reached` (its own check, which runs on the numbers the server just checked, so in production it fires only if the two builds disagree), it sends `Launch` → `CapHit{kind: attempts}` → `Sessions`, in that order, and logs `rubato.cap.hit`. Whether that hit blocks follows the existing rule for companion cap hits (its `at` against the server's launch time), as for spend. (AC1)
- **S3** — When someone launches the issue again with a higher `attempt_limit`, the launch goes through and the issue is no longer *Blocked* (a cap hit older than the latest launch does not block; existing rule).

## 3. Where it changes

- `rubato-server` — `src/launch/handler.rs`: on `attempt > attempt_limit` log the event, record the cap hit, `notify("cap hit")`, then answer 409. `src/launch/store.rs`: the live cap hit per issue comes with its kind. `src/overview/{inputs.rs,build.rs}`: an `attempts` hit does not block while a session for the issue is live (the overview is where launches and sessions meet; `launch` cannot name `companion_link` without a cycle).
- `rubato-companion` — `src/launch/arm.rs`: after an `AttemptLimitReached` refusal send `CapHit{attempts}` and log the event.

## 4. Caveats triage

- Contract compatibility: no schema change. `CapHit` and `CapKind::Attempts` are already in `schema/protocol/cap_hit.json`; the server's `CapHit` arm already handles any kind. A message the contract defined is now sent in the case it was defined for.
- Idempotency: each refused attempt adds a `cap_hits` row; the read takes `MAX(at)` per issue, so repeats do not change the outcome.
- Authorisation: unchanged entry point (`POST /api/launch`, `CurrentUser`); a user can only trigger this for an issue they could launch.
- Observability: O1, O2. The event is at `warn`.
- Derived, not stored (project): N5.
- Seam O-row (project): both seams have one.
- Testability: the server test needs a connected companion for the first launch; `Harness::pair` and `connect` already do that.
- n/a: Boundaries, Concurrency, Schema change, Cost, Telemetry names (the event name exists), Own tmux only (N3), Check reports its count, Log level — no new table, name, check or path to another user's machine.

## Review outcome

design-reviewer, 2026-11-10: 1 blocker, 2 should-fix.

- **Spec check:** Does: gap (S1 did not say what happens while a session is live, and the code would turn a running issue *Blocked*). We'll know it works: ok for S1–S3 as first written, missing the live-session case. Must not break: missing that neighbour. Debug at 3 am: gaps (O2 named a 409 that `internal()` does not return and a log line with no issue; O1's first action could not be done from the web).
- **Track check:** small holds: no migration, no contract change (`attempts` is already in the cap-hit schema), no new consumer, dependency or auth change. The seam's traffic changes; its contract does not.
- **Fixed:** S4, T5 and N7 (an attempts hit does not block a live issue; decided in the overview, where launches and sessions meet); S5 and O2 (event before the write; a failed write is logged with the issue and still answers 409); O1's first action; the order `Launch` → `CapHit` → `Sessions` in S2.
- Accepted: a companion-sent cap hit keeps the companion's timestamp, so clock skew can stop it blocking — it is the existing behaviour for spend hits, and changing it would change the spend path too (A3).
