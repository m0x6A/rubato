# Alerts reach someone, page rules to OnCall and ticket rules to email

Small track. The 16 "never silent" rules are on the Grafana stack and evaluate cleanly (health
`ok`, checked 2026-11-25 with `gcx alert rules list --folder rubato`). Nobody hears about them,
though. The stack's notification policy tree has root receiver `empty` and no routes, so
`CompanionSilent`, firing that day, reached nobody. The tree is shared with other teams on the
stack, so Rubato does not edit it. Each rule names its own contact point through the import
route's `X-Grafana-Alerting-Notification-Settings` header.

## What the change does

- `observability/alerts/receivers.json` maps a rule's `severity` label to a contact point:
  `page` → `m0x6a` (Grafana OnCall), `ticket` → `pantrypilot-email` (email).
- `observability/publish.ts` splits each rule group by severity and sends each part as its own
  group, `<group>-<severity>` (`rubato-page`, `rubato-ticket`), with the receiver header. The
  Prometheus rules file and its promtool tests do not change.
- Before the first write, the publish fails when a rule has no severity, a severity has no
  receiver, or a receiver is not a contact point on the stack.
- After the groups are written, a group in the Rubato folder that the files no longer produce is
  deleted (today's single `rubato` group, which would otherwise evaluate every rule twice). A dry
  run names it and deletes nothing. Nothing is deleted unless at least one group was written.

## How we'll know it works

- [ ] `observability/publish.test.ts`: the committed rules go out as `rubato-page` (5 rules) and
  `rubato-ticket` (11 rules), each with its receiver header.
- [ ] Must fail: a rule without a severity, a severity with no receiver, and a receiver the stack
  does not have each fail before any write.
- [ ] A group the files no longer produce is deleted after the writes; a dry run deletes nothing
  and says what it would delete.
- [ ] After the merge, `publish-observability` runs, and then `gcx alert rules list --folder
  rubato` shows the two groups, 16 rules, health `ok`, and no group `rubato`.
- [ ] One rule fired on purpose reaches its contact point. `CompanionSilent` is firing already
  (no companion running), so the OnCall page follows the first publish.

## What it must not break

- The rules themselves: same expressions, labels and `for`; `pnpm observability:rules` (promtool
  tests, including the must-fail file) passes unchanged.
- Other teams' alerting: the policy tree, other contact points and other folders are not
  touched. The delete only reads and removes groups in the Rubato namespace.
- The dashboards' publish and the read-back of every group.

## How we'll debug it at 3 am

The publish logs one line per group with its receiver, and one per group deleted. On the stack,
`gcx alert rules list --folder rubato` shows each rule's state and health. Notification history
(`gcx alert notification-history`) shows whether a firing rule was delivered to its receiver.
