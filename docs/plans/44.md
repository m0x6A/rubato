# One list of session statuses and sources; cap hits judged on the server's clock

Issue: #44 · Track: small · Branch: `issue/44-status-lists`

## 1. Problem

To report a zero for every status and source (#26), the lists were written out by hand in
`crates/rubato-companion/src/sessions/registry.rs` (`STATUSES`, `SOURCES`) and again in
`crates/rubato-server/src/companion_link/ws.rs` (`record_sessions_by_state`). A new
`SessionStatus` variant compiles without either list changing, and that status then never reports
zero. The label for a status was `format!("{status:?}").to_lowercase()`, which matches serde only by
luck of single-word variants.

From #30 (plan `docs/plans/30.md`, A3): a companion-sent cap hit is stored with the companion's
clock (`cap_hits.at = hit.at`) and compared with the server's `launches.created_at`. A companion
clock that is behind makes a live hit look older than the launch, so the issue does not show
*Blocked*.

**Acceptance criteria** (from the issue)

- [x] **AC1** — one list in `rubato-protocol` (`SessionStatus::ALL`, `StateSource::ALL`) with a test that it covers every variant, used by both binaries.
- [x] **AC2** — the companion clock no longer decides whether its cap hit is live.

## 2. Spec

### 2.1 What the change does

- **S1** — `SessionStatus::ALL` and `StateSource::ALL` list every variant, and `name()` gives each one's wire spelling. A protocol test compares both lists with the variants in the type's JSON Schema and with serde, so adding a variant fails the test until it is listed. (AC1)
- **S2** — The companion's gauges (`rubato.sessions.by_state`, `rubato.sessions.discovered`) and the server's `rubato.sessions.by_state` take their zeros from those lists and their labels from `name()`; the hand-written lists and the companion's `source_name` are gone. Label values are unchanged. (AC1)
- **S3** — When the server receives a cap hit from a companion, it stores its own receive time in `cap_hits.at`; the companion's time stays in the payload. The server's own attempts hit (launch handler) is already stamped with its clock. (AC2)
- **S4** — A cap hit is live when the issue was never launched, or when no newer run superseded it. A hit that names a session whose launch the server stored (`LaunchCommand.session_id`, the `--session-id` Claude was started with) is live unless a launch *started* after that one; a second Start refused as `already_running` does not supersede the run. Any other hit (attempts, or a session the server never launched) is live when the server received it at or after the issue's latest launch was stored. (AC2)
- **S5** — The server's `rubato.cap.hit` warn on receipt carries `rubato.session_id`, so a hit judged stale can be matched to its launch from the logs.

## 4. Caveats triage

- Contract compatibility: no schema change. `ALL` and `name()` are Rust items, not serialised; `schema/protocol/*.json` and `web/src/protocol.ts` do not change (N5). Both binaries build against the same protocol crate, so the lists cannot disagree.
- Idempotency: a replayed envelope is deduplicated on `(companion_id, seq)` and acked without storing (`companion_link/ws.rs`, `record_event`), so a replay adds no row. The late-delivery case is an outbox flush after a reconnect: an attempts hit buffered on companion A that arrives after a launch on companion B gets a receive time after that launch and looks live. That is harmless: an attempts hit does not block while a session is live (N3), and the issue had just used up its attempts. A spend hit is matched by session, so late delivery cannot make it belong to a newer run.
- Telemetry names: unchanged; label values unchanged.
- Derived, not stored: liveness is still read at query time from `cap_hits` and `launches`.
- n/a: Boundaries, Concurrency, Schema change (no migration; `cap_hits.at` keeps its type, only who stamps it), Authorisation, Cost, Check reports its count (the protocol tests print theirs), Log level.

## 7. Decisions

- **D1** — tie a session's hit to its launch by session id, not by a new field · because `LaunchCommand.session_id` is the `--session-id` the companion starts Claude with, so the spend hit already names its launch, and a `launch_id` on `CapHit` would be a schema change (full track per the profile) · rejected: `launch_id` on `CapHit`; receive time for every hit (a replayed spend hit from an earlier run would look live).
- **D2** — the variant test reads the JSON Schema · because schemars lists every variant the type has, so the test needs no list of its own · rejected: an exhaustive `match` only (catches a new variant at compile time but not one missing from `ALL`).

## Review outcome

design-reviewer, 2026-11-12: 1 blocker, 1 should-fix; both taken.

- **Spec check:** Does: ok. We'll know it works: gap (no row for a later launch that was refused or failed). Must not break: ok. Debug at 3 am: ok; suggested `session_id` on the receipt warn.
- **Track check:** small holds: no change under `schema/`, `web/` or `migrations/`, no new consumer, dependency, boundary or auth change.
- **Fixed:** the first rule matched a spend hit only against the issue's latest launch of any result, so a second Start refused `already_running` would drop the running session's spend hit (a regression of "cost caps block"). S4 now supersedes a run only by a launch that *started* after it, with the test `a_spend_hit_blocks_after_a_second_start_was_refused_as_already_running`. The idempotency caveat was rewritten (replays are deduplicated on `seq`; the real case is an outbox flush). S5 adds `rubato.session_id` to the warn.
