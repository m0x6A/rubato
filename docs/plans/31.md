# Dashboard: show map staleness

Issue: #31 · Track: small · Branch: `issue/31-map-staleness`

## 1. Problem

The "Map" stat panel shows only `rubato_map_loaded` and `map_load_failures`. Whether the map is
fresh is visible only in the `map loaded` log lines and in `loaded_at` from `/api/map`: the
accepted gap on the `server-system-map` O-row of `docs/plans/20.md`.

**Acceptance criteria** (from the issue)

- [ ] **AC1** — a dashboard panel shows how old the loaded map is.

Prior art: design #20 §11 and the `server-system-map` O-row in `docs/plans/20.md`.

## 2. Spec

### 2.1 What the change does

- **S1** — When the server loads the map (from GitHub or from a file), it records the gauge `rubato.map.loaded_at` with the load time in unix seconds. When a reload fails and the server keeps the cached map, the gauge keeps its old value. (AC1)
- **S2** — When someone opens the dashboard, a stat panel "Map age" in the Map row shows `time() - max(rubato_map_loaded_at)` in seconds. On a healthy server it saw-tooths up to the reload cycle, which is longer than 300 s: `lcm(poll interval, 300)` seconds of sleep plus the time each poll takes plus the 60 s export interval (about 6–7 min at the default 60 s poll interval; 10 min at 120 s). The panel turns yellow at 900 s and red at 1800 s and grows without bound when reloads stop or keep failing. (AC1)
- **S3** — When a map load fails because the file cannot be read or the YAML does not parse, `rubato.map.load_failures` counts it (today only fetch and validation failures do), so the "Map" panel next to "Map age" shows the cause.
- **S4** — When the server starts with a stored map (`warm`), it records the gauge with the stored load time, so a restart during a GitHub outage shows the real age instead of No data.

## Review outcome

design-reviewer, 2026-11-10: 1 blocker, 2 should-fix; all taken. The reviewer confirmed the gauge semantics: with the SDK's cumulative temporality a gauge recorded only at load time is re-exported every interval, so `time() - max(…)` keeps growing. (With `OTEL_EXPORTER_OTLP_METRICS_TEMPORALITY_PREFERENCE=delta` it would not; the "Companions" panel has the same dependency.)

- **Spec check:** Does: ok. We'll know it works: gap (nothing tested "keeps its old value" or the `warm` recording; the must-fail case for the check had no file). Must not break: gap (N1's guards only cover a successful reload). Debug at 3 am: "past 300 s" fires on a healthy server; the failure counter misses read and parse errors.
- **Track check:** small holds: no migration, schema, consumer, dependency or auth change.
- **Fixed:** the in-memory metric test (S1, S3, S4, N1); `check.test.ts` with a must-fail copy; the healthy bound stated and thresholds at 900 s and 1800 s (S2, O1); failures counted at the read and parse sites (S3); no unit on the gauge (N4).
