# Interactive flow view, issues from the app, and one planning workflow

Issue: #71 · Design: [71-flow-view-and-issues/design.md](71-flow-view-and-issues/design.md) ·
ADRs 0024–0028 (accepted 2026-11-12). Seven PRs on `issue/71-*` branches; PR 0 is this plan.

This is the first plan in the ADR 0027 form. Track, review and approval are not kept here. The
review is posted on #71 as a `Review:` comment, and approval is a `Approved: plan <sha>` comment by
a person.

## What the change does

- **Scenarios.** The map can declare scenarios: ordered steps over the declared flows. The map view
  plays one step by step, with a data or control pulse moving across each seam (ADR 0024).
- **New issue here.** A person can create an issue from a part or seam. The GitHub App writes it
  under #71's headings, and it is pinned where it was started (ADR 0025).
- **`Map:` line.** An issue whose body has a `Map: node|seam <id>` line is placed on the map
  without anyone dragging it. An unpinned issue without the line gets a suggested place that a
  person confirms with one click (ADR 0026).
- **Review and approval.** Both are derived from `Review:` and `Approved:` comments and shown per
  issue, with an earlier-version warning (ADR 0027).
- **One planning workflow.** The rubato skill becomes the only planning workflow in this repo, and
  the feature-workflow profile is retired (ADR 0028).

## How we'll know it works

- [ ] The e2e test plays "start a session on an issue" step by step, with and without reduced motion.
- [ ] A map with a step that is not a declared flow fails to load in Rust and in plan-check, with the same fixture.
- [ ] Data and control steps look different without colour (a filled dot and a ring), checked in the map-view test and the e2e test.
- [ ] An issue created from the `rubato-server` part appears pinned on it, in both e2e projects (dev and app).
- [ ] The rendered body matches a snapshot: #71's headings in order, checkboxes under "How we'll know it works", the creator in backticks with no bare `@`, then the `Rubato-Request:` and `Map:` lines. The form refuses to send without each required section.
- [ ] Submitting a request id twice makes one issue. A timed-out create is found by its `Rubato-Request:` line on the next listing. Unpinning an issue made in the app sticks after a tick.
- [ ] A `Map:` line or a `Review:` comment from a non-member is not trusted: the line becomes only a suggestion (`untrusted_author`), and the review shows no badge.
- [x] Ticking a task keeps an approval current; editing the spec makes it stale. Tested with two `issue/71-*` branches and `on <branch>`.
- [ ] A fixture issue with `Map: seam web-server` appears on that seam. After an unpin it stays unpinned.
- [x] An `Approved:` comment from a Bot or a non-member is ignored. An approval of an older blob raises `ApprovalStale`.
- [ ] `plan.ts init` writes none of `track`, `review`, `approval` or `status`. plan-check reports `legacy_keys` for the existing plans and still passes them.

## What it must not break

- The structure, data, control and plan lenses, drag-to-pin, and the shared layout.
- Maps without scenarios, and ADR 0017 flows.
- Map proposals (ADR 0018) and `can_write` semantics.
- The ADR 0023 call budget: no new GitHub calls per tick for `Map:` lines or comments.
- `Decision:` comments (ADR 0014).
- The progress model: approval is a badge, not a state.
- CI over the existing `docs/plans/*.md`, and the skill installed in connected repos.
